# Контракты ролей

[English](../../role-contracts.md) · [Русский](role-contracts.md) · [Deutsch](../de/role-contracts.md) · [简体中文](../zh-CN/role-contracts.md)

Команда задаёт состав и скилы, профиль — модели, Markdown-файлы команды — ограниченные
инструкции исполнения. Корневой контракт — `teams/<team>/coordinator.md`, не отдельный субагент.


Исходник роли — `teams/<team>/agents/<role>.md`: TOML-метаданные между
разделителями `+++`, затем инструкции Markdown. Команды независимы, даже если
названия ролей совпадают. Модели остаются в профилях, привязки skills — в `team.toml`.

Обязательные поля: `name`, `description`, `access` (`read-only` или
`workspace-write`), логические `web` и `delegation`. Для роли без права записи
делегирование запрещено. Codex наследует sandbox, согласования и MCP основного чата;
в TOML ролей не записываются `sandbox_mode` и `approval_policy`. Ограничение «только
чтение» остаётся инструкцией, а не отдельным sandbox Codex. Claude использует список
инструментов для ролей без записи, Antigravity — явный список инструментов.
Права клиента и полномочия поручения продолжают действовать.
Редактируйте исходник команды и обновляйте установку, а не сгенерированные роли.

Роли Claude с `delegation = false` также запрещают нативный инструмент `Agent` через `disallowedTools`, включая роли с доступом к записи.

## Формат инструкций

Для root-координатора и субагентов используйте одинаковые блоки. Начните с краткого назначения и условий выбора роли. Затем:

| Раздел | Содержание |
|---|---|
| Skill activation, при необходимости | Предпосылки, загружаемые инструкции и доказательства запуска |
| Working mode | Порядок действий, входы и обработка отсутствующих входов |
| Focus on | Особенности поручения |
| Quality checks | Доказательства завершения |
| Return | Пути, результаты, замечания и решения |
| Boundaries | Область записи, делегирование и остановки |

Формулируйте действия кратко и одинаково для трёх клиентов. Не создавайте второго
универсального координатора, квоту замечаний или обязательный вызов необязательных ролей.
У каждой роли один исходник внутри своей команды; рендереры создают нативные форматы клиентов.

В координаторах используйте Markdown-заголовки; назначение и блоки соответствуют исходникам ролей. Явно отделяйте маршрутизацию и интеграцию root. Координатор загружается скиллом Plex, а не регистрируется дополнительным нативным субагентом.

## Обязательная оценка задачи

Память помогает продолжению работы; используйте весь доступный контекст сессии и
принятые требования. Отсутствие детали в checkpoint не отменяет её без нового решения.

Новая память координатора хранится в Markdown; старый JSON остаётся читаемым.
Проверяющий скрипт выводит любой из форматов в Markdown через `--markdown`, не меняя
исходник. Setup автоматически переносит корректные JSON-файлы памяти выбранной
установки в Markdown: проверяет результат, сохраняет резервную копию и убирает
старые файлы. Конфликты сохраняются и отображаются в статусе; `plex status`
показывает формат памяти. Проверка старого пути возвращает новый `canonical_path`
той же сессии. Вместимость — 32 КиБ UTF-8 и 16 текущих решений; сохраняйте точные ссылки
и имена исполнителей. Предел хранения не ограничивает контекст или выполнение.

После оценки Dev/DevOps самостоятельно выполняет обычные технические шаги внутри
принятого задания. Эскалация, альтернативные инструменты и независимая работа во
время ожидания приёмки следуют [общему правилу](../../../skills/plex/references/assignments.md#execution-ownership).

После активации Plex координатор ведёт короткое [состояние сессии](../../../skills/plex/references/coordinator-state.md). Связанные followup изменяют текущий результат; несвязанные запросы можно сначала записать в очередь без делегирования. До маршрутизации или исполнения новой или отложенной задачи требуется короткая оценка `plex-pm`. Root сам не определяет сложность и готовность к реализации. PM возвращает класс задачи, цель и исключения, недостающие решения, роли и порядок, принятый формат и ссылку задачи, контракт для dev с проверками и готовность (`ready`, `needs-specialist`, `blocked`).

В команде BMad эта короткая оценка не активирует персону, меню, PRD или Build. Настоящие BMad-поручения следуют своим контрактам входа. Постановка оформляется по существующему процессу проекта: tracker, issue, spec или story; используйте поддерживаемую операцию PO или отдельный spec-workflow из каталога. Прямой workflow следует собственному контракту и не требует несвязанной персоны. Нельзя навязывать `bmad-spec` всем версиям или создавать параллельное хранилище задач.

Нужные технические решения передаются архитектору в BMad или PM в pnet до dev. Подробное требование или маленький diff не доказывают готовность решения. Для уже оценённых шагов и неизменного продолжения оценка переиспользуется; существенные решения вне её границ возвращаются PM. Отсутствующая или отклонённая роль блокирует своё поручение: root может собрать ограниченный контекст и сообщить статус, но не заменяет её проектирование или реализацию. Это обязательный результат специалиста, а не новое согласование пользователя.


## Разбор задачи и выбор маршрута

Каждая задача Plex, выбранная для маршрутизации, начинается с короткого маршрута: результат, нужные роли,
порядок работы и проверка завершения. Root координирует; существенное планирование
и реализацию передаёт владельцам ролей. В скилле есть следующие
[маршрута работы](../../../skills/plex/references/task-flows.md):

| Задача | Маршрут |
|---|---|
| Ограниченная задача с понятной целью и критериями | оценка PM → dev → обязательные проверки → координатор |
| Крупная новая работа с нерешёнными вопросами | оценка PM → нужные PM/PO/UX/architect → dev → проверки → координатор |
| Причина сбоя неизвестна | оценка PM → ограниченная диагностика → исправление → проверки → координатор |
| Запрошено ревью | оценка PM → reviewer → координатор |
| CI/CD, релиз или назначенное развёртывание | оценка PM → devops → обязательные проверки/review → координатор |

Общие [правила маршрутизации задач](../../../skills/plex/references/task-flows.md) определяют, когда нужны Architect или UX; эти роли подключаются по необходимости, а не на каждом этапе.

При неизвестной причине сбоя завершайте диагностику, когда путь и причина уже
позволяют безопасно исправить код. Неопределённость идентичности или эффектов в
production блокирует ACK, replay или изменение данных, но не изолированный фикс,
который безопасно удерживает неизвестные случаи.

Используются только роли выбранной команды: в pnet техническое планирование тоже
принадлежит PM; в BMad есть отдельные PM, PO, UX и архитектор. Готовые планы
переиспользуем, решённые вопросы пропускаем; при изменении границ или предположений
возвращаемся к нужному специалисту. Выбор маршрута не добавляет согласование;
проверки workflow и разрешение на аналитика сохраняются. Мелкая механическая
задача может остаться у root.

Для маршрутизации BMad PM один раз читает полную карту `workflows` из точного
снимка, переданного root, и возвращает минимально достаточный маршрут: назначение,
подходящую роль, вход, последовательность и ожидаемые канонические входы/результаты.
При интерактивных вариантах root запускает маршрут, выбранный пользователем; иначе —
зафиксированный маршрут PM. Root интегрирует результат и не выбирает собственную альтернативу.

## Обязанности

| Роль | Результат |
|---|---|
| pm | Первичная оценка, выбор маршрута и критерии; в BMad — требования, PRD и назначенный отдельный spec-workflow |
| explorer | Карта нужного кода и проверок без изменений |
| researcher | Внешние первичные источники и неопределённости |
| analyst | Ограниченное исследование предметной области; в BMad только по запросу/согласованию |
| po | Спецификации и задачи BMad, разбиение на тикеты, учёт и перепланирование |
| ux | Реализуемые пользовательские сценарии, состояния и дизайн |
| architect | Технические границы, инварианты и решения |
| dev | Реализация и проверки; выбранный workflow исполнения BMad |
| reviewer | Независимые замечания с местом, триггером, влиянием и доказательствами |
| qa | Независимая проверка поведения и тесты в своей области |
| devops | CI/CD, публикация релизов и назначенное развёртывание/восстановление с доказательствами для точной версии |

DevOps — нативный специалист Plex в обеих командах; он использует релизные/deployment-процедуры проекта без обязательной BMad-персоны. Оценка PM сохраняется. Разрешение на релиз не означает разрешение на развёртывание; подготовка, публикация, установка и работоспособность требуют отдельных доказательств. Независимое ревью остаётся у reviewer.

Доступны роли выбранной команды. У каждого изменяемого файла один владелец.
Возврат различает проверки, предположения, сбои стенда и пробелы. Используйте годные
доказательства повторно, после правок проверяйте затронутое. Дополнительное полное
ревью требует нового риска, существенного изменения или прямого запроса.

## Запуск BMad

- Персона/меню: активировать объявленную персону, затем выбранную операцию.
- Отдельный workflow: использовать его собственный контракт активации и возврата, не запуская несвязанную персону или меню.
- Reviewer активирует workflow ревью напрямую; вложенный исполнитель выполняет свой рецепт, не перезапуская родительский workflow.
- Стартовый отчёт и итог содержат путь скилла, доказательства активации,
  workflow/операцию и достигнутый шаг. Приветствия или имени роли недостаточно.
- Координатор подтверждает активацию только после получения доказательств.
- Ограниченная задача идёт в Build без обязательной внешней цепочки планирования.
  Диагностика кода, план реализации, review и исправления остаются у Build.

## BMad

Активируйте существующие скилы, не копируйте персоны и меню конкретной версии.
Сохраняйте выбранный отрендеренный маршрут, обязательные циклы и настоящие согласования.
Ранний переход пропускает поздние checkpoint этого шага: проверяйте условие и цель
до эскалации. Исправляйте ложный gate в том же поручении, не выдумывая одобрение.
Готовая спецификация сама по себе не причина для остановки.

Для реализации используйте конкретные уже принятые требования. Если их нет,
выбранный spec- или Build-маршрут формирует их до начала кода; не создавайте
автоматически PRD, epic, story или дублирующую спецификацию. В `interactive` PM
передаёт root существенно разные маршруты и рекомендацию для вопроса пользователю;
в `auto` выбирает без необязательного вопроса о маршруте. `balanced` сохраняет
прежнюю политику. Уже выбранный маршрут используется повторно, а контрольные точки
workflow остаются обязательными.

Вложенная работа требует полномочий и свободного лимита. Сохраняйте промпты листовых
исполнителей и контекстные контракты; не направляйте листовое ревью в обёртку полного
workflow. Сообщайте реальные модели, маршруты и недоступные возможности.

## Проверка требований и независимое ревью реализации

- До начала кода по новым или существенно изменённым исполняемым требованиям BMad нужна семантическая проверка с помощью поддерживаемой операции установленной версии и адаптера проекта (PO `VALIDATE`, если поддерживается). Build может до неё исследовать проблему, проводить диагностику, планировать и готовить рабочую spec. В доказательствах укажите установленную версию, реально выполненную операцию и адаптер, точные идентификаторы/ревизии исходных требований, значимых приложений и актуальных решений человека (либо каноническую ревизию, которая их фиксирует), релевантные сценарии/зависимости, конечные критерии приёмки, замечания и их статус. Повторно используйте доказательства, только если весь набор входных данных не изменился. Если Build подготовил новые исполняемые требования, координатор приостанавливает только реализацию кода, направляет именно эту spec на PO `VALIDATE` или установленный эквивалент без нового PM intake, затем после устранения существенных пробелов возобновляет работу того же Dev с безопасной точки. Отсутствие нужной возможности блокирует только реализацию по этим требованиям. Проверка структуры задания и активация персоны не являются семантической проверкой. Уже принятую работу продолжайте с её текущим владельцем; не перезапускайте её задним числом только ради новых доказательств.
- До принятия реализации требуется независимое code review точного кандидата и требований, если человек явно не переопределил это правило. Завершённое применимое независимое ревью внутри Build считается один раз; если оно отсутствует или его выполнение не доказано, направьте точный кандидат отдельному reviewer. Зафиксируйте ревизии, независимость reviewer, замечания и их статус; повторно используйте доказательства только при неизменных кандидате и требованиях, а существенные изменения направляйте на ревью. Более позднее явное решение человека остаётся главным. Не добавляйте второе полное ревью после завершённого применимого внутреннего ревью.

## Задания, планирование и цели

В pnet PM отвечает за постановку, технический план и способ исполнения. В BMad PM
проводит intake, PO оформляет спецификации/задачи, architect принимает технические
решения. Root организует маршрут и собирает доказательства; нового менеджера не добавляем.

Исполняемые задания используют [короткий контракт](../../../skills/plex/references/assignments.md)
и валидатор без записи файлов. Укажите входные данные, разрешённые изменения/исключения,
принятые зависимости, готовность и обычно три наблюдаемых критерия (от одного до пяти),
каждый со способом проверки. Используйте существующие issue/spec/story. Первичный PM
intake и вложенные задания workflow не требуют дополнительного Plex-контракта.
Валидатор проверяет структуру, а не содержательную готовность, sandbox или реальный вызов.
Лимит критериев относится к сводке задания; все проверки исходной spec/workflow сохраняются.

PM/PO выбирает `normal`, `plan` или `goal` с обоснованием; в `auto` — без дополнительного
вопроса о режиме. Plan закрывает решения до изменения приложения; goal последовательно
доводит принятое задание до проверенных критериев. Native-режимы необязательны: иначе
используются обычный план или ограниченная работа до результата с честным описанием
фактического подхода. Нельзя скрыто переключать чат, заменять существующую цель или
обещать продолжение, которого нет у клиента. Разрешения хоста и выбор пользователя сохраняются.

Для подходящей автономной разработки BMad в `auto` выбирается установленный
`bmad-build-auto`: одна итерация rendered workflow с его обязательными субагентами
и итоговым статусом. Иначе — разрешённый поддерживаемый маршрут Build. Спецификацию,
renderer, проверки и реальные gates сохраняем; второй полный цикл планирования/review не добавляем.

Повторно используйте агента. Передавайте новые решения, изменившиеся доказательства и
оставшийся вопрос вместо всей истории. Независимые оценки выполняются параллельно,
зависимая работа ждёт принятых входов. Противоречия возвращаются владельцу решения
без выдуманного консенсуса. Итог связывает каждый критерий с доказательством и пробелами.

`max_agents` ограничивает одновременно незавершённые задания Plex, а не все запуски
за сессию. Завершённое/idle-задание освобождает этот лимит, но его handle может занимать
нативный слот: перед блокировкой проверьте оба ограничения отдельно.

## Проверяемый возврат и запрос помощи

Новые Plex-задания получают метку и положительную `revision`. Общий
[контракт ответа](../../../skills/plex/references/assignments.md#response-contract)
проверяет роль, идентичность задания, статус и evidence по критериям до приёмки.
Прежний CLI проверки входа совместим; для ответа используется
`check_assignment.py --resolved <snapshot> --assignment <current-assignment.md>`
с Markdown-ответом на stdin. Задания и ответы используют фиксированные заголовки, поля
и списки из шаблонов; JSON остаётся совместимым входным форматом. Один контракт
передаётся прямо в сообщении без внешнего блока кода и без дублирующей JSON-копии.
Валидатор сохраняет JSON-диагностику. Обе проверки ничего не записывают.

- `progress`: новый результат/наблюдение и следующий шаг; ждать подтверждения не нужно.
- `needs-decision`: конкретный вопрос, выполненные проверки и рекомендация;
  координатор направляет его PM/PO, архитектору или владельцу входных данных/разрешения.
- `blocked`: реальное ограничение, evidence и условие возобновления зависимой работы.
- `completed`: все критерии задания выполнены с evidence; принимающая роль ещё
  проверяет результат. Reviewer может завершить работу возвратом найденных дефектов.

`completed` завершает только это задание. PM/PO формулирует исходную цель пользователя
и сохраняет конечного ответственного и проверку результата в существующей передаче;
координатор закрывает цель только после проверки объединённых evidence. Завершённое
предварительное задание не означает доставку результата: успешная сборка может быть
предварительным этапом, а запрошенное работающее развёртывание требует проверки
указанной целевой среды. В многоэтапной работе переданный результат фиксируется в
[состоянии координатора](../../../skills/plex/references/coordinator-state.md), а у
верхней цели обновляется `next_action`; блокировка следующего этапа не открывает
переданный результат заново.

Если метод получения evidence недоступен или не работает по причине самого метода,
используйте поддерживаемую альтернативу в пределах того же разрешённого действия и
объёма, сохраняя критерии приёмки и обязательные проверки; не запрашивайте разрешение
только ради смены метода. Отказ хоста, изменение действия/объёма/эффектов, выход за
границу хоста или неясные полномочия передаются действительному владельцу разрешения.

Продолжает тот же исполнитель с новыми данными, исправленным входом или решением.
Нельзя открывать прежнюю проблему под новой меткой или перезапускать весь workflow.
Один раз верните автору ошибку оболочки ответа с точной диагностикой. Сохраните
ранее проверенные evidence с исходным артефактом, ревизией и происхождением;
повторяйте работу или проверки только если evidence изменились или стали
недействительными. Не добавляйте evidence за автора. Если исправленный ответ всё ещё
неверен, сохраните и сообщите частичный результат, не требуя бесконечного
переформатирования. Обновления событийные: без таймера, нового лимита токенов и
автоматической смены модели.

Первичный PM intake и внутренние шаги workflow сохраняют свои форматы. Во внешнем
ответе BMad по-прежнему нужны доказательства активации и выполнения workflow.
Старые контракты без идентичности читаются; для новой проверки добавьте идентичность,
не перезапуская активную работу. Обновите Plex и откройте новую сессию клиента для
загрузки инструкций. Проверка структуры не доказывает качество evidence, не исключает
все циклы и не перехватывает native dispatch; поведение проверяется отдельно.

Координатор проверяет продвижение к следующему наблюдаемому результату приёмки.
Повторяющиеся статусы требуют точечной сверки артефакта или результата проверки,
а не нового круга планирования. Владелец, блокер и следующий шаг в checkpoint
должны соответствовать текущему принятому заданию. Если исполнитель продвигается,
он продолжает работу без повторных запросов статуса. См. [контроль исполнения](../../../skills/plex/references/assignments.md#coordinator-supervision).
