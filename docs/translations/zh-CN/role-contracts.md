# 角色契约

[English](../../role-contracts.md) · [Русский](../ru/role-contracts.md) · [Deutsch](../de/role-contracts.md) · [简体中文](role-contracts.md)

团队定义成员和技能，配置档选择模型，团队的 Markdown 源文件提供有边界的执行指令。
根协调者契约位于 `teams/<team>/coordinator.md`，不是额外的子智能体角色。


角色源文件位于 `teams/<team>/agents/<role>.md`：`+++` 分隔的 TOML 元数据，
随后是 Markdown 指令。即使角色同名，各团队仍独立。模型保留在配置档中，技能绑定保留在 `team.toml` 中。

必填字段为 `name`、`description`、`access`（`read-only` 或 `workspace-write`），
以及布尔字段 `web` 和 `delegation`。只读角色不能启用委派。
Codex 从主会话继承沙箱、审批设置和 MCP 服务器；生成的 TOML 不包含 `sandbox_mode` 或 `approval_policy`。
只读边界由行为指令约束，不构成独立的 Codex 沙箱。
Claude 为只读角色使用工具允许列表，Antigravity 使用显式工具列表。
客户端权限及任务授权仍然有效。请修改团队源文件并刷新安装，不要直接修改生成的角色文件。

Claude 中 `delegation = false` 的角色还会通过 `disallowedTools` 禁用原生 `Agent` 工具，包括具有写入权限的角色。

## 格式

根协调者和子智能体使用相同的内容块。先简述目的和选择条件，再包含以下部分：

| 部分 | 内容 |
|---|---|
| Skill activation（按需） | 前提、要加载的指令及启动证据 |
| Working mode | 执行顺序、输入及缺失前提的处理 |
| Focus on | 当前角色的重点 |
| Quality checks | 完成所需证据 |
| Return | 路径、结果、未决发现或决策 |
| Boundaries | 写入范围、委派权限和停止条件 |

使用简明、具体的步骤，并保持各客户端语义一致。不创建通用的第二协调者，不设置任意发现数量，
不强制调用可选角色。每个角色在其团队内只有一个源文件，由客户端渲染器生成原生格式。

协调者使用 Markdown 标题，目的和内容块与角色源文件保持一致。明确根协调者负责的路由与整合。协调者由 Plex 技能加载，不注册为额外的原生子智能体。

## 必须先评估任务

激活 Plex 后，协调者维护精简的[每会话状态](../../../skills/plex/references/coordinator-state.md)。相关 followup 更新现有结果；无关请求可先记录为待处理而不派发。路由或执行新请求、待处理请求前，必须由原生 `plex-pm` 简短评估。Root 不自行判断复杂度或实现就绪状态。PM 返回目标与非目标、缺失决策、所需角色及顺序、项目任务格式与引用、开发契约及检查，以及 `ready`、`needs-specialist` 或 `blocked`。

在 BMad 团队中，这种角色内评估不激活 persona、菜单、PRD 或 Build。后续真正的 BMad 任务遵循各自的入口契约。需求使用项目已有的 tracker、issue、spec 或 story 流程；可使用受支持的 PO 操作或目录中的独立 spec workflow。直接 workflow 按自身契约进入，无需先激活无关 persona。不强制所有版本提供 `bmad-spec`，也不引入平行任务存储。

实现前，必要的技术决策交给 BMad 的 architect 或 pnet 的 PM。详细需求或较小的 diff 并不证明设计已就绪。已覆盖步骤和未改变的继续工作复用评估；超出范围的新决策返回 PM。所需角色缺失或被拒绝时，仅阻塞该任务；root 可收集有限上下文并报告状态，但不能接管其设计或实现。这要求专家产出，不增加用户审批。


## 任务接收与路由

每项已选定路由的 Plex 任务先简述路线：预期结果、所需角色、执行顺序和完成检查。
根协调者负责协调，将重要规划和实现交给对应角色。技能中定义了以下
[工作路线](../../../skills/plex/references/task-flows.md)：

| 任务 | 路线 |
|---|---|
| 目标和验收明确的有边界修改 | PM 评估 → dev → 必需验证 → 协调者 |
| 存在未决事项的重要新任务 | PM 评估 → 所需 PM/PO/UX/architect → dev → 验证 → 协调者 |
| 故障原因未知 | PM 评估 → 有边界的诊断 → 修复 → 验证 → 协调者 |
| 请求审查 | PM 评估 → reviewer → 协调者 |
| CI/CD、发布或指定部署 | PM 评估 → devops → 必要检查/审查 → 协调器 |

仅使用所选团队角色：pnet 的 PM 也负责技术规划；BMad 分设 PM、PO、UX 和架构师。
复用已接受的计划，跳过已解决的问题；范围或假设变化时再咨询对应专家。
路线选择不增加用户批准关卡，工作流必需检查和分析师授权规则仍有效。
小型机械修改可由根协调者直接完成。

BMad 路由由 PM 选择：PM 从 root 传入的准确快照中读取完整 `workflows` 映射一次，
返回最小充分路线、用途、适用角色、入口、顺序以及预期的规范化输入/输出。
若 interactive 提供路线选项，Root 分派用户确定的路线；否则分派 PM 确定的路线。
Root 整合结果，不另行替换所选路线。

## 职责

| 角色 | 负责结果 |
|---|---|
| pm | 首次评估、路线选择和验收；BMad PM 负责产品需求、PRD 及被选中的独立 spec 工作 |
| explorer | 相关代码及已有检查的只读地图 |
| researcher | 外部一手资料与不确定性 |
| analyst | 有边界的领域研究；BMad 中仅在用户直接要求或批准后调用 |
| po | BMad 规格/任务工作流、任务拆分、跟踪和重新规划 |
| ux | 可实现的用户流程、状态和设计 |
| architect | 技术边界、不变量和决策 |
| dev | 实现与验证；所选 BMad 执行工作流 |
| reviewer | 带位置、触发条件、影响和证据的独立发现 |
| qa | 独立行为检查及授权范围内的测试 |
| devops | CI/CD、版本发布及明确指定的部署/恢复，提供对应修订的证据 |

DevOps 在两个团队中均为原生 Plex 专家，使用项目的发布/部署流程，不强制要求 BMad 角色。仍需 PM 评估。发布授权不代表部署授权；准备、发布、安装和运行健康状态需要分别提供证据。独立审查仍由 reviewer 负责。

只有团队包含的角色才可用。每个被修改文件只有一位责任人。
返回结果应区分检查、假设、harness 故障和缺口。复用有效证据，修改后重跑受影响检查。
额外完整审查应由新风险、实质修改或明确请求触发。

## BMad 启动

- Persona/菜单分派：激活声明的入口 persona，再启动所选操作。
- 直接独立 workflow：遵循所选 workflow 自己的激活和返回契约，不先启动无关 persona 或菜单。
- Reviewer 直接进入审查 workflow；叶子执行者遵循指定配方，不重新启动父 workflow。
- 启动报告和最终返回应列出技能路径、激活证据、工作流或操作及已进入的步骤。
  问候语或角色名称不能证明执行。
- 协调者仅在获得执行证据后确认激活。
- 有边界的修改直接交给 Build，无需额外的强制规划链。
  Build 保留自己的调查、实现计划、审查和修复。

## BMad 契约

激活已有技能，不复制角色人格，不假定版本菜单。遵守渲染后的路线、必需循环和真实用户关卡。
适用的提前退出会跳过当前步骤后续检查点；升级给用户前先核对条件与目标。
错误关卡在同一任务内修正，不能虚构批准。规格已写好本身不是请求批准并暂停的理由。

实现应复用已接受的具体需求。若尚不存在，由选定的 spec 或 Build 路线在编码前
产出具体需求；不要自动创建 PRD、epic、story 或重复规格。在 `interactive` 下，
PM 通过 root 向用户提供差异明显的路线和建议；在 `auto` 下自行选择，不提出可选的
路线问题。`balanced` 保持原规则。已确定的路线不再重复询问，真实 workflow 检查点仍然有效。

嵌套委派需要权限与容量。保留叶子任务提示词及上下文契约，不将叶子审查交给会重新启动完整工作流的包装角色。
报告实际路由和不可用能力。

## 任务契约、计划与目标

pnet 由 PM 负责任务定义、技术计划和执行方式。BMad 由 PM 初评、PO 编写规格与任务、
architect 处理技术决策。Root 负责调度和整合证据，不增加 manager 角色。

可执行任务使用[简洁契约](../../../skills/plex/references/assignments.md)及只读验证器。
包含输入、写入范围与排除项、已接受的依赖、就绪状态及通常三个可观察验收标准（最少一个，
最多五个），每个标准都有验证方法。复用现有 issue/spec/story。首次 PM 初评及 workflow
内部子任务不需要额外 JSON 契约。结构验证不能证明内容就绪、沙箱权限或真实委派。
标准数量上限仅适用于交接摘要，不得删除原规格或 workflow 要求的任何检查。

PM/PO 说明理由并选择 `normal`、`plan` 或 `goal`；`auto` 下不再次询问执行方式。
Plan 在修改应用前解决决策问题；goal 在已接受的范围内迭代至验收通过。
客户端原生模式是可选能力：不可用时照常规划或进行有限的目标导向执行，并报告真实方式。
不得暗中切换聊天模式、替换已有目标，或承诺客户端不支持的自动续跑。仍须遵守用户选择与宿主权限。

BMad 在 `auto` 下适合无人值守开发时选择已安装的 `bmad-build-auto`：执行一轮渲染后的
workflow，保留其必需子代理和终止状态。否则使用获授权且受支持的 Build 路径。
保留规格、renderer、检查和真实人工关卡，不额外套一轮完整规划或审查。

复用代理实例；只传递新决策、变化的证据与剩余问题，不广播完整历史。
独立评估可并行，依赖任务等待已接受的输入。把冲突结论交回决策负责人，不虚构共识。
最终结果将每个验收标准与实际证据及缺口对应。

`max_agents` 限制同时未完成的 Plex 任务，不是会话累计启动次数。
已返回或空闲任务不再占用该额度，但其句柄可能仍占原生线程槽；报告容量阻塞前应分别核对两者。

## 经验证的返回结果与求助

新的 Plex 任务具有任务标签和正整数 `revision`。
[统一响应契约](../../../skills/plex/references/assignments.md#response-contract)
在验收前检查角色、任务身份、状态及各验收项的证据。原有输入检查 CLI 保持兼容；
响应检查使用 `check_assignment.py --resolved <snapshot> --assignment <current-assignment.json>`，
通过 stdin 传入 JSON 响应。两种检查均不写入文件。

- `progress`：新的结果或观察及下一步，无需等待确认。
- `needs-decision`：具体问题、已执行的检查和建议；协调器将其转交 PM/PO、架构师或输入/权限负责人。
- `blocked`：真实限制、证据及恢复相关工作的条件。
- `completed`：所有任务验收项均已通过且有证据；接收方仍需验收。审查者可以通过提交缺陷报告完成任务。

`completed` 仅完成该任务。PM/PO 负责界定用户的上层目标，并在现有交接中保留
该目标的终态负责人和具体检查；协调器只有在整合后的证据通过该检查后才能关闭
上层目标。已完成的前置任务不等于交付：构建成功可以完成一个前置任务，而用户
要求可运行的部署时，仍需检查指定目标环境。

如果证据方法不可用，或因方法本身的问题失败，应在同一授权操作和范围内改用
受支持的方法，并保留验收标准和必需检查；不要仅为更换方法而再次请求权限。
宿主拒绝、操作/范围/影响改变、跨越宿主边界或权限不明确时，转交实际权限负责人。

由同一执行者根据新证据、修正的输入或明确决策继续工作。不得换个标签重开同一
问题或重新启动整个工作流。将一次响应格式修正及准确诊断交回原作者。保留
此前已验证证据及其原始工件、修订版和出处；仅当证据改变或失效时才重做
工作或检查。不要代替作者补充证据。修正后仍无效时，保留并报告部分结果，
不无限要求重新格式化。进展按事件报告，不引入定时器、新 token 上限或自动模型切换。

初始 PM 评估与工作流内部步骤保留原有格式。外层 BMad 返回仍须包含激活与工作流
执行证据。旧契约仍可读取；为新响应检查补充身份，不重启正在进行的工作。
刷新 Plex 并打开新客户端会话以加载指令。结构有效不等于证据可靠，也不能保证
消除所有循环或强制原生派发；实际运行行为需另行验证。
